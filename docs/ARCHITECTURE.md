# TimeFocus — ארכיטקטורה ומערכת ה-ML

```
                  ┌──────────────────── זמן אמת (כל ~4 שנ׳, < 1ms) ─────────────────────┐
 ActivityMonitor ─► snapshot ─► context ─► RealtimeClassifier ─► FocusController ─► התערבות
 (AX, URL, טקסט,     (אפליקציה,  (מזהה      ├ שיוך קיים (משתמש/LLM/אשכול)   (תוכנית היום,    ├ תזכורת (HUD/התראה)
  ספירת קלט, מדיה)    כותרת, אתר)  יציב)     ├ רשת תלמיד (MLP)              סטייה/ביטחון/     ├ האטה הדרגתית (SIGSTOP duty-cycle)
                                            ├ אב-טיפוסים + חידוש (novelty)   חידוש)            └ שאלה על פעילות לא מוכרת
                                            └ מסנן זמני (HMM)
                  └──────────────────────────────────────────────────────────────────────┘
                                    ▲ ModelBundle (החלפה אטומית)
                  ┌──────────────── זמן פנוי בלבד (IdleScheduler) ─────────────────────┐
  A. e5 רב-לשוני ← B. LLM מתאר כל פעילות ← C. e5 על התיאורים ← D. ייצוג רב-מבטי + גרף מעברים
  ← אשכול / שיוך לאב-טיפוסים ← E. LLM zero-shot + שמות ← F. גילוי סוגים חדשים ← G. אימון התלמיד ← H. פרסום
                  └───── כל מודל נטען רק בשלב שלו ומשוחרר מיד; ביטול תוך ~1 שנ׳ כשהמשתמש חוזר ─────┘
```

## 1. מעקב (FocusCore/Tracking)

- **Snapshot** כל 4 שנ׳ + מיידית במעבר אפליקציה/חלון/לשונית (NSWorkspace + ‏AXObserver): אפליקציה, כותרת (מנוקה ממונים ושמות אפליקציה), URL (‏AXURL → שורת כתובת → AppleScript), טקסט גלוי (סריקת עץ AX בתקציב של 350 צמתים/0.6 שנ׳, לא נוגעת בשדות סיסמה), ספירת קלט (מוני window server — ללא הרשאה וללא תוכן), וידאו מתנגן (IOPM assertions).
- **Context** = מזהה יציב `hash(bundle | host | path-head | title)`. **Segment** = רצף זמן בקונטקסט אחד (עד 10 דק׳). כל מרווח זמן משויך לקונטקסט *הקודם* (זה שהיה על המסך בזמן המרווח). זמן ללא קלט > 2 דק׳ (ללא וידאו) = "לא ליד המחשב".
- **התנהגות** מצטברת לכל קונטקסט: הקלדות/קליקים/גלילות/תנועות לדקה, שבר זמן מדיה, שעה ממוצעת (ממוצע מעגלי).

### טקסט מאזור התוכן בלבד (ContentRegion, ‏Boilerplate)

לשוניות, שורת כתובת, סרגל סימניות, תפריטים וסרגלי צד מציגים את אותו טקסט בכל חלון — הם לא אומרים במה החלון משמש, ו"גונבים" את השורות הראשונות שהמודלים רואים (ה-e5 רואה כ-12 שורות, ה-LLM כ-20). לכן הטקסט נקרא רק מאזור התוכן, בשלוש שכבות:

1. **מבנה (Accessibility)** — `ContentLocator`:
   - **מה שנמצא באמצע החלון**: ‏hit-test בנקודת המרכז (`AXUIElementCopyElementAtPosition`) ועלייה דרך ההורים — כ-15 קריאות במקום סריקת העץ (הסרגל של Arc לבדו מכיל מאות אלמנטים, והסריקה נגמרה לפני שהגיעה לדף — נמצא בבדיקה חיה). אם בדרך יש דף — זה הדף; מסמך שממלא את רוב הדף (מציג ה-PDF של Chromium, שסרגל הכלים שלו הוא הדף החיצוני; אפליקציה בתוך iframe) הוא התוכן עצמו. סריקת העץ נשארת כגיבוי.
   - **דף אינטרנט** (דפדפנים, Electron): אזור הדף הגלוי = ‏AXWebArea ∩ ה-AXScrollArea שמעליו ∩ החלון (ב-Safari ה-web area הוא כל המסמך; ב-Chromium/Firefox הוא ה-viewport). בתוכו מחפשים landmarks בקריאה אחת (`AXUIElementsForSearchPredicate` עם `AXLandmarkSearchKey` — אותו API שמשמש את ה-rotor של VoiceOver): אם יש `AXLandmarkMain` גלוי — קוראים רק אותו, ואם יש בתוכו עמודות זו לצד זו — רק את העמודה שאמצע החלון נמצא בה (האב החיצוני ביותר במסלול ה-hit-test שרוחבו 45–85% מה-main וגובהו לפחות חצי; ב-YouTube ה-main מכיל גם את ההמלצות — נמצא בבדיקה חיה); אחרת חותכים מהקצוות navigation/complementary/banner/contentinfo (עמודה בגובה מלא בצד — ימין או שמאל, אתרים בעברית הפוכים — או רצועה ברוחב מלא למעלה/למטה), ולא יותר מ-60% בכל ציר. הטקסט נקרא בסריקת העץ מאותו אלמנט, רק מה שמוצג באזור: אלמנט מחוץ לאזור מדולג עם כל מה שבתוכו, וכך גם תוויות של פיקסל-שניים שמיועדות רק לקורא מסך ("Chat mode", "Use the arrow keys…"). כל אלמנט נקרא בקריאה אחת (`AXUIElementCopyMultipleAttributeValues`). בדף עמוק מדי לתקציב הסריקה — הטקסט שהדף מציג באזור דרך text markers ‏(`AXStartTextMarkerForBounds` → ‏`AXStringForTextMarkerRange`).
   - **דף שעדיין נטען** (אין עדיין web area בעץ): נקרא כ"דף" ולא כ"תוכן", כך שסינון הפריסה עדיין חל עליו, וקריאת טקסט ריקה חוזרת אחרי כ-5 שנ׳ ולא אחרי 20.
   - **יישום רגיל**: החלונית הגדולה ביותר (scroll area / text area / web area) שאינה סרגל צד. macOS לא מסמן סרגלי צד באופן אמין (source list מדווח כ-AXOutline רגיל), ולכן הם מזוהים לפי צורה: צרים (≤30% מהרוחב), גבוהים, צמודים לקצה.
2. **פריסה (בתמונה, כשאין אזור תוכן מובהק)** — `OCRLayout`: ה-OCR מחזיר בלוקים; "עמודה ראשית" נקבעת לפי הבלוק עם הכי הרבה טקסט רץ (≥5 מילים לשורה) עם העדפה למרכז, ובלוקים של שורות קצרות שנמצאים לצידה (ניווט, תוכן עניינים, רשימת ערוצים) או רצועות בקצה העליון/התחתון של התמונה (תפריט, footer) נזרקים.
3. **זיכרון שורות חוזרות** — `BoilerplateFilter`: לכל יישום (ובדפדפן — לכל אתר) נשמרים 24 החלונות האחרונים ובאילו מהם הופיעה כל שורה (hash של השורה בלי ספרות, אותיות גדולות ופיסוק — "3 הודעות" = "12 הודעות"). שורה שהופיעה ב-≥3 חלונות וב-≥60% מהם היא תבנית ונזרקת; שורה שמופיעה רק בחלק מהדפים (שם הקורס בדפי הקורס) נשארת. הזיכרון חסום (עד 1,500 שורות לכל תבנית, עד 64 תבניות) ונשמר ב-kv.

### OCR בעברית (OCRService, ‏OCRFusion, ‏TesseractOCR)

ה-OCR של Apple ‏(Vision, כל ה-API שלו) לא תומך בעברית גם ב-macOS 27, ו-Apple Intelligence (שמקבלת תמונות ב-macOS 27) ממציאה טקסט בעברית ואיטית (14–21 שנ׳). לכן:
- **צילום**: ScreenCaptureKit של החלון בלבד, 2 פיקסלים לנקודה (גם במסך 1×, כי Tesseract צריך אותיות גבוהות), חיתוך לאזור התוכן. אם טביעת האצבע של התמונה (dHash ‏33×32) לא השתנתה מאז הקריאה הקודמת של אותו חלון — לא קוראים שוב.
- **Vision** ‏(accurate, ‏בלי language correction — על מסך עברי היא פי 3 יותר איטית ולא מוסיפה) קורא אותיות לטיניות. על עברית הוא מחזיר כלום או רעש בביטחון 0.3–0.5, ועל לטינית ~1.0.
- **Tesseract** ‏(`heb` מ-tessdata_best, תהליך-בן קצר בעדיפות נמוכה, התמונה עוברת ב-pipe ולא נכתבת לדיסק, TSV עם תיבה וביטחון לכל מילה) קורא עברית. במודל `heb` אין אותיות לטיניות — הוא "מתרגם" אנגלית לאותיות עבריות בביטחון ≤0.76.
- **מיזוג מילה-מילה** (`OCRFusion`): שורה של Vision (בביטחון ≥0.8) מחליפה את מה שמודל העברית קרא מתחתיה — אם לכל היותר רבע מהמילים שלה יושבות על עברית ש-Tesseract בטוח בה (≥0.85), זו שורה לטינית, והעברית שם היא קריאה שגויה של מילים לטיניות ("for" ← "זסז"). אחרת זו שורה עברית ש-Vision הפך חלקית לרעש (על עברית מודגשת הוא מחזיר "vonnx", ‏"pınıka", ‏"OI" בביטחון 1.0 — נמצא בבדיקה חיה), ואז מילה-מילה: עברית בטוחה מנצחת, ושאר המילים של Vision נכנסות. Vision גם לא מצליח להפריד עברית שצמודה למילה לטינית, ולכן כשהתיבה שלו רחבה בהרבה מהטקסט (יותר מ-0.8 גובה-שורה לתו) נשארות מתחתיה המילים העבריות, והמקטע הלטיני מצטמצם לרווח שהן משאירות. סדר המילים בשורה: מימין לשמאל כשהעברית שולטת.
- **מבט שני על מילים באנגלית בתוך שורה בעברית**: Vision מפספס אותן לעתים קרובות (deploy, ‏staging, ‏code review בשורה עברית), אבל מודל העברית מסמן את מקומן — מילים בלי אותיות עבריות, בביטחון נמוך, או ספרות (אותיות גדולות הופכות אצלו לספרות: "OCR" ← "068"). רצף כזה בשורה נחתך (מוגדל פי 2 כשהטקסט קטן) ונקרא שוב ב-Vision; מספר אמיתי פשוט חוזר כמו שהוא. כיוון השורה נקבע לפי מספר המילים (עבריות מול לטיניות, בלי שברי מילים), לא לפי מספר האותיות.
- נמדד על דפים אמיתיים (‏2560 פיקסלים רוחב): ‏0.1 שנ׳ ל-Vision ו-0.3–1.5 שנ׳ ל-Tesseract לעמוד שלם. בפעם הראשונה ש-Vision רץ בתוכנה חדשה macOS מכין את המודל שלו כחצי דקה (בעיקר המתנה, כ-4.5 שנ׳ CPU); אחר כך זה נשמר.
- **מה נכנס לטקסט של החלון**: רק שורות OCR שרוב המילים שלהן לא נקראו כבר דרך Accessibility (שקפים בווידאו, PDF, תמונות, canvas). כשטקסט ה-Accessibility עשיר (≥1,500 תווים) ה-OCR רץ בתדירות נמוכה פי 3.

## 2. המודל בזמן אמת — "רשת התלמיד" (FocusML/NN/StudentNetwork.swift)

```
  hashed bag: app, host, path, title words+bigrams+Hebrew prefix-variants, char-3grams, text words
      (לכל שדה "תקציב משקל" קבוע — דף טקסט ארוך לא מטביע את זהות האתר)
  ─► EmbeddingBag 65,536×64 (ממוצע משוקלל)  ⊕  9 תכונות צפופות (התנהגות, שעה, דפדפן)
  ─► Linear 192 + ReLU + Dropout ─► Linear 128 + ReLU = z
        ├► ראש סמנטי 384 + L2-norm   ← distillation (cosine) מה-e5
        └► ראש סיווג K + softmax      ← סוגי הפעילות (CE משוקלל, label smoothing)
```
- Backprop ידני על Accelerate (sgemm), ‏Adam לשכבות צפופות ו-LazyAdam לשורות ה-embedding שנגעו בהן.
- **אוגמנטציות שמלמדות עמידות לשינוי תוכן**: הפלה אקראית של שדה שלם (טקסט 35%, כותרת 15%, נתיב 30%…) — הרשת לומדת לזהות סוג פעילות גם כשהתוכן חדש; ו"ביטחון התנהגות" אקראי (0/חלקי/מלא) — חלון חדש שנצפה שניות ספורות מקבל התנהגות "ממוצעת" במקום ערכים חריגים.
- תוצאות (בדיקות): דיוק אימות 100% על נתונים סינתטיים, **100% על כותרות עם מילים שלא נראו מעולם וללא טקסט**, התאמה סמנטית ל-e5 ‏(cos) ≈ 0.93–0.98.

**החלטה בזמן אמת** (RealtimeClassifier): קונטקסט שכבר הוסבר (שיוך משתמש 0.97 / LLM 0.85 / אשכול) — משתמשים בשיוך. אחרת — *product of experts* של (א) הסתברויות התלמיד ו-(ב) דמיון לאב-טיפוסים במרחב הייצוג, כשהייצוג נבנה מהפלט הסמנטי של התלמיד. **חידוש** (novelty) = sigmoid של המרחק מסף האב-טיפוס של הסוג. בסוף — מסנן HMM (הישארות 0.92 באותו קונטקסט, 0.55 במעבר) נגד "הבהובים".

## 3. הלמידה בזמן פנוי (FocusCore/Learning)

**IdleScheduler**: מתחיל רק אחרי N דקות ללא קלט, בלי וידאו מתנגן, לא בסוללה חלשה/חום; פעם ב-45 דק׳ לכל היותר. שעון עצר בודק כל 0.75 שנ׳ — נגיעה במקלדת/עכבר ⇒ ביטול, שחרור המקודד והריגת שרת ה-LLM.

| שלב | מה | מודל |
|---|---|---|
| A | ייצוג סמנטי לכל קונטקסט חדש/שהשתנה: `query: App | Title | host | path | text…` | multilingual-e5-small (מנוע Swift שלנו, ‏3.5ms לטקסט) |
| B | תיאור מופשט: `{activity, category (19 קטגוריות), topic}` | LLM מקומי (llama.cpp/Gemma או Apple) |
| C | ייצוג סמנטי של התיאור | e5 |
| D | ייצוג רב-מבטי + אשכול/שיוך | מתמטיקה |
| E | שיוך zero-shot של חלונות חדשים לסוג קיים + הצעת שמות בעברית | LLM |
| F | גילוי סוגים חדשים, מילות מפתח (c-TF-IDF לפי מקור — ר׳ "הסבר לסוגי הפעילות"), אפליקציות מובילות | — |
| G | אימון התלמיד מאפס על כל הנתונים המתויגים (replay מלא — אין "שכחה") | — |
| H | שמירת `ModelBundle` והחלפה אטומית במסווג | — |

**ייצוג רב-מבטי** (RepresentationBuilder) — וקטור אחד מנורמל שמאחד:
1. e5 של הטקסט הגולמי (ממורכז לפי ממוצע הקורפוס של המשתמש — מסיר את ה-anisotropy של טרנספורמרים),
2. e5 של התיאור המופשט של ה-LLM ("studying linear algebra course material"),
3. **עוגנים סמנטיים zero-shot**: דמיון ל-18 תיאורים דו-לשוניים של סוגי פעילות כלליים, **מכויל** לכל עוגן מול הקורפוס (z-score, "contextual calibration") ו-softmax,
4. זהות אפליקציה/אתר (hashing), 5. התנהגות (z-scores חתוכים).

לאחר מכן **החלקה על גרף המעברים** (שלב GCN אחד): חלונות שעוברים ביניהם שוב ושוב באותה סשן (עורך ↔ טרמינל ↔ תיעוד) נמשכים זה לזה — סוג פעילות נלמד כ"תהליך עבודה" ולא רק כטקסט דומה. מעברים נדירים (הסחה חד-פעמית) כמעט לא משפיעים.

**אשכול (שלב האיסוף)**: איחוד כמעט-כפולים (cos ≥ 0.9, "הרצאה 3"/"הרצאה 4"), ‏average-linkage משוקלל בזמן (אלגוריתם NN-chain, ‏O(n²)), בחירת K בטווח 3–10 לפי silhouette משוקלל על הקבוצות הייחודיות, קיפול סוגים קטנים (<1.5% מהזמן), ושמירת מזהים וצבעים יציבים בין ריצות (התאמה חמדנית לפי חפיפה).

**אחרי מתן השמות** — הסוגים "קפואים" והלמידה אינקרמנטלית:
1. חלון חדש ← **אב-טיפוסים מרובים לכל סוג** (k-means כדורי) — אם לא "חדש" ועם מרווח ← שיוך,
2. אחרת ← **LLM zero-shot** ("לאיזה מהסוגים שייכת הפעילות הזו? 0 אם אף אחד") ← שיוך,
3. אחרת ← אשכול של החלונות הבלתי-מוסברים; קבוצה עם ≥20 דק׳ ← **סוג פעילות חדש** + הודעה למשתמש.

### הסבר לסוגי הפעילות (ActivityEvidence)

מסך "סוגי פעילות" מראה לכל סוג על מה המודל התבסס, כדי שאפשר יהיה לתת שם, לאחד או לפצל על סמך מה שבאמת היה על המסך — ולא רק לפי שם האפליקציה (ב-Claude, למשל, הכותרת תמיד "Claude"). לכל סוג מחושבות מילות מפתח **לפי מקור** — הטקסט שנקרא מהחלון, כותרות החלונות, כתובות האתרים ונושא ה-LLM — ב-c-TF-IDF (מילים שכיחות בסוג ונדירות באחרים), ולצדן התיאורים של ה-LLM, הקטגוריות שלו, דפוס השימוש (הקלדה/גלילה/מדיה, שעה אופיינית) והחלונות עצמם — לכל חלון: המילים שמייחדות אותו, איך שויך, והשורות הראשונות של הטקסט שנקלט. טקסט של הממשק עצמו מסונן: מילות פונקציה בעברית ובאנגלית (רשימה נפרדת — המאפיינים של רשת התלמיד לא משתנים), מילות ממשק נפוצות, מילים שיישום מציג כמעט בכל החלונות שלו בכמה סוגים (סרגלים, תפריטים), שורות של מילה-שתיים במשקל נמוך, תיאורי אייקונים, שם היישום עצמו, וספירות רוויות. תחיליות בעברית ("באפליקציה") נספרות תחת מילת הבסיס, ומילים שכמעט תמיד מופיעות צמודות מוצגות כצירוף ("אלגברה לינארית"). אותן מילים נשמרות על הסוג ונכנסות להנחיה שבה ה-LLM מציע לו שם. החישוב (עשרות מילישניות) רץ מחוץ ל-main thread בחיבור נפרד למסד.

### איך המערכת מתמודדת עם שינוי תוכן (concept drift)

הבעיה: "עבודה" בשבוע הראשון נראית אחרת מ"עבודה" על משימה חדשה; יחידה 5 בקורס מכילה טקסט אחר מיחידה 1. הפתרון משלב כמה שכבות:
- **ייצוג סמנטי** (e5 רב-לשוני): "ערכים עצמיים" ו"מרחבי מכפלה פנימית" קרובים זה לזה ול-"linear algebra" גם בשפות שונות.
- **הפשטה ע"י LLM**: לכל יחידה חדשה — "studying linear algebra" — תיאור זהה גם כשהטקסט שונה לגמרי. (נבדק: יחידה 9 שלא נראתה מעולם סווגה ל"לימודים" בביטחון 0.8.)
- **עוגנים zero-shot** ו**גרף מעברים** — סוג הפעילות וההקשר שבו היא מתרחשת, לא המילים.
- **אב-טיפוסים מרובים** — סוג פעילות יכול לכסות כמה פרויקטים/קורסים, ומתרחב כשנוספים חברים חדשים.
- **אימון מחדש** של התלמיד בכל ריצה עם הפלת-שדות — הוא לומד להסתמך על אפליקציה/אתר/התנהגות כשהטקסט חדש.
- **חידוש ≠ עונש**: חלון חדש לגמרי מקבל "לא בטוח" (ללא האטה), נשאלת שאלה, והתשובה הופכת לתווית משתמש (המשקל הגבוה ביותר באימון).

## 4. מיקוד והתערבות

**FocusController** — מכונת מצבים לכל יום: `onTrack / offTrack / uncertain / neutral / noPlan`. סטייה = הסתברות ≥ סף (0.65–0.8 לפי רמת ההקפדה) שהפעילות מחוץ לסוגים המותרים בבלוק (+ "מותר תמיד"). פרופיל "רגיל": תזכורת 15 שנ׳, האטה מ-45 שנ׳, עלייה ליניארית ל-85% תוך 5 דק׳, תזכורת חוזרת כל 3 דק׳. חזרה ⇒ שחרור מיידי ותיעוד "אפיזודת סטייה".

**ProcessThrottler** — חוט בעדיפות גבוהה: בכל מחזור של 250ms ‏`SIGSTOP` לתהליך היעד וכל צאצאיו (ב-Safari גם תהליכי WebContent) למשך `level × 250ms` (עם jitter), ואז `SIGCONT`. מעל 25% גם `PRIO_DARWIN_BG` (E-cores + הגבלת I/O). נמדד: ב-80% תהליך עמוס מקבל ~10% CPU ומתאושש מיד ל-100%. **בטיחות**: אף פעם לא: TimeFocus, ה-watchdog, תהליכי מערכת קריטיים, משתמש אחר, יישומי "לעולם לא להאט"; התהליכים שמושהים בכל מחזור נרשמים (pid + זמן התחלה) לקובץ מצב, ותהליך **`tf-watchdog`** נפרד — בינארי זעיר עם שם אחר, כך ש-`killall TimeFocus` לא מפיל גם אותו — ממתין (kqueue) ליציאת האפליקציה מכל סיבה (כולל `kill -9`) ומשחרר רק את מה ש-TimeFocus השהה ועדיין עצור, מחזיר עדיפות, ועוצר llama-server שנשאר; בלי watchdog חי אין האטה בכלל. תהליך שמישהו אחר עצר (למשל job ב-Ctrl-Z) לעולם לא "נחטף" ולא מחודש; בהפעלה מחדש מתבצע recovery; SIGTERM/יציאה משחררים הכל; ‏`⌃⌥⌘.` = עצירת חירום.

**שעון הסטייה** סופר רק זמן off-track רציף (עד 12 שנ׳ בין דגימות): זמן נעילה/היעדרות, חלונות "לא בטוח", פרטיים או TimeFocus עצמו לא נספרים — כך שאין קפיצה להאטה מקסימלית אחרי חזרה למחשב. תוכניות ו"מותר תמיד" עוקבים אחרי איחודים (merged_into), כך שאיחוד סוגים לא הופך עבודה מתוכננת ל"סטייה".

## 5. זיכרון ו-CPU

| מצב | RAM |
|---|---|
| רגיל (מעקב + תלמיד) | ~50MB |
| למידה: e5 (fp16, ממופה לזיכרון) | +~100MB, משוחרר מיד |
| למידה: Gemma 3 1B / 4B דרך llama.cpp | +~1.2GB / ~3.5GB, רק כשהמחשב פנוי; התהליך נהרג בסוף השלב |

ה-e5 וה-LLM לעולם לא בזיכרון באותו זמן.

## 6. מודל הנתונים (SQLite, WAL)

`contexts` (זהות, טקסט, התנהגות מצטברת, embeddings, תיאור LLM, שיוך + מקור), `segments` (ציר זמן + מצב מיקוד + רמת האטה), `clusters` (שם משתמש / מוצע / אוטומטי, מילות מפתח, צבע, איחודים), `feedback`, `plans` (JSON לכל יום), `episodes` (סטיות), `kv` (מטא של המודלים, עוגנים, מצב הלמידה). כל תת-מערכת עם חיבור משלה: tracking (תור המעקב), ui (main), pipeline (תחת בעלות-ריצה), stats (תחת נעילה).

## 7. תהליכונים

- `timefocus.tracking` (סדרתי): snapshot → context → סיווג → החלטה → התערבות. היחיד שנוגע ב-trackingStore/classifier/controller.
- main: UI, AppleScript (עם timeout של 2.5 שנ׳ מתור המעקב), HUD, התראות.
- Task מנותק: צנרת הלמידה. חוט ההאטה. תהליך watchdog.
